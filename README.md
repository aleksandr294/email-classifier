# Email Classifier Service

## Description

REST API service that accepts an `.eml` file, parses it, and classifies the email using an LLM (Claude).
Every classification is stored in the database and can be retrieved later by its ID.
Submitting the same file twice returns the existing result without re-classifying.

- Swagger — http://localhost:8000/api/docs
- ReDoc — http://localhost:8000/api/redoc

The execution commands are stored in the `Makefile`.

## Examples

Upload an `.eml` file, then fetch the result by its ID (the API answers `201` immediately with `status: "pending"`,
or `200` with the existing record if the same file was already uploaded):

```bash
curl -X POST http://localhost:8000/api/v1/classify/ -F "file=@email.eml;type=message/rfc822"
curl http://localhost:8000/api/v1/classify/<id>/
```

Categories: `spam`, `phishing`, `newsletter`, `transactional`, `personal`, `automated`.
Statuses: `pending` → `processing` → `classified` (or `failed`, which the retry worker re-queues).
Ready-made samples are generated by `python scripts/make_eml_samples.py` (`datasets/eml/`) and
`python scripts/make_injection_eml.py` (`datasets/injection_eml/`). The JSON below is real service output (`claude-haiku-4-5`), shortened.

## Architecture

Classification is handled **asynchronously** via a dedicated worker process rather than inside the HTTP request:

```
POST /classify/
    │
    ├── validate .eml
    ├── compute SHA-256 hash  →  duplicate? return 200 with existing record
    ├── persist record (status=pending)
    └── return 201 immediately
                │
                ▼
    [classify worker — polls every N seconds]
        ├── claim one pending record (SELECT ... FOR UPDATE SKIP LOCKED → status=processing, commit)
        │   (no DB transaction is held during the LLM call)
        ├── parse .eml → call Anthropic Claude (tool use)
        ├── confidence ≥ 0.6 and no injection detected  →  status=classified
        └── confidence < 0.6 or injection detected  →  status=pending, retry → status=classified, reviewed=true
                │
    [retry worker — polls every 10 min]
        ├── reset failed → pending for re-processing
        └── reset stale processing (worker crash, > STALE_PROCESSING_MINUTES) → pending
```

**Why async over synchronous classification:**

A synchronous approach (classify inside the HTTP handler) would tie up an API worker thread for the duration of the LLM call — typically 2–5 seconds. Under moderate load this leads to thread exhaustion, increased latency for all endpoints, and cascading timeouts. The async worker model decouples ingestion from classification: the API responds in milliseconds, and the worker processes records at its own pace without affecting API throughput.

**Scaling path — message broker:**

The current worker uses DB polling (`SELECT FOR UPDATE SKIP LOCKED`), which is simple and works well at low-to-medium throughput. If DB polling becomes a bottleneck at high load (many concurrent uploads, high query rate on the `classification_record` table), the classify worker can be migrated to consume from a message broker (RabbitMQ, Redis Streams) with minimal changes — the `POST /classify/` handler publishes a job instead of relying on a DB status field, and the worker subscribes to the queue. The rest of the codebase stays unchanged.

## Prompt injection protection

Emails are untrusted input, so the classifier is hardened in several layers (none of them is a guarantee on its own):

- the email is sent to the LLM as a **JSON data block** (`from`, `to`, `date`, `subject`, whitelisted `headers`, `body`), so email text cannot close a delimiter or fake extra fields;
- text is normalized first: NFKC, invisible / bidi / control characters removed, body truncated to 20 000 characters;
- the system prompt declares every email value (sender name, subject, headers, hidden HTML) to be data, never instructions;
- the output is forced through a tool with an enum `category`, so the model cannot return free text;
- the model reports `injection_detected`; such emails always go through a second review pass (`reviewed=true`).

A targeted benchmark (26 attacks + 3 benign controls: body, subject, sender name, headers, hidden HTML, Unicode, nested messages, ...) lives in `datasets/injection_eml/`.
With the API and the classify worker running:

```
python scripts/make_injection_eml.py
python scripts/eval_injection.py
```

## Requirements

- Python 3.12+

- Docker

## Setup

1. **Clone repository:**

   ```
   git clone git@github.com:aleksandr294/email-classifier.git
   cd email-classifier
   ```

2. **Install Poetry:**

   ```
   pip install poetry
   ```

3. **Install dependencies:**

   ```
   poetry install
   ```

4. **Set .env file:**

   ```
   cp .env.example .env
   ```

   Fill in the variables:

   ```env
   POSTGRES_URL=postgresql+asyncpg://user:user@localhost:15000/test_db
   ANTHROPIC_API_KEY=your_anthropic_api_key
   LLM_MODEL_NAME=claude-haiku-4-5-20251001
   ```

   Optional: `CLASSIFY_WORKER_PAUSE_SECONDS` (10), `RETRY_WORKER_PAUSE_SECONDS` (600), `STALE_PROCESSING_MINUTES` (15).

5. **Start local database:**

   ```
   make up_local_environment
   ```

6. **Apply migrations:**

   ```
   make migrate
   ```

7. **Run API:**

   ```
   make run_api
   ```

8. **Run workers** (separate terminals):

   ```
   make run_classify
   make run_retry
   ```

## Run full stack (API + workers + PostgreSQL)

```
docker build -f docker/Dockerfile.base -t email-classifier-base:latest . && docker compose -f docker-compose.yml -p email-classifier-system up --build
```

## API

#### POST /api/v1/classify/
#### GET /api/v1/classify/{id}/

Response fields: `id`, `status`, `category`, `confidence`, `reasoning`, `signals`, `reviewed`, `injection_detected`.
For detail information see Swagger
